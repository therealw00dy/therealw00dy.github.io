## [Self-Assessment](https://github.com/therealw00dy/therealw00dy.github.io/blob/main/Self-Assessment.docx)

I am a student finishing a Bachelor of Science in Computer Science at Southern New Hampshire University, with a heavy interest in backend and full-stack development. This capstone gave me a reason to go back through work from previous classes and see how my work and mindset have changed. My capabilities and the issues I look for when reviewing and writing code have changed completely; over the last few years, I've become much more aware and confident in my coding. The biggest change is how I treat my own code. In the past, I was mostly worried about the program running and working as intended, but now I look for how it can fail, how someone else can read it, and how I can prove that it works. These changes in mind and skill set are very visible in the differences found in my code from reworking it to a higher standard than when I designed it.

Working with feedback from someone else was a regular part of this capstone. Initially, I recorded a code review of my work, then received instructor feedback on choices that could be made with enhancements or artifact choices. After feedback on Enhancement One, I added more detail to how my components work with each other and increased my testing. After feedback on Enhancement Two, I added a complexity analysis and checks for prerequisites that are not real courses. After feedback on Enhancement Three, I added the ability to add and remove prerequisites, as well as tests for the database. This is the same setup I feel I could expect from a team code review or working as a team in any capacity in this field.

I have worked extensively with my skills as a team member, leader, and representative. In many previous courses, I was tasked with breaking down technical jargon into relatable and understandable communication with stakeholders or anyone similar. This also has real-life implications for me in the Navy Reserves, as I am in the middle of enlisted ranks; it is often my job to communicate between lower enlisted and upper enlisted, moving between different levels of professionalism and clear communication. In a computer science related scenario, I am building a fantasy sports application that combines four different sports together in one fantasy application. This application stemmed from an idea with friends, giving me the same idea of communicating with more non-technical people and building off of that, as I need to ask them for ideas and preferences on how they imagine parts of the application being built so I can satisfy the requests of as many people as possible.

In my data structure work, I had compared vectors, hash tables, and binary search trees on the same data and viewed runtime and memory before deciding on a hash table for my initial course planner. In this capstone, I went back and improved the decision by replacing the hash function with one that worked better by differentiating anagram course numbers, added dynamic resizing, and built a directed graph of prerequisites. A depth-first search finds any circular prerequisites, and Kahn’s algorithm produces a valid order for taking courses. Reworking this has also helped me learn to state trade-offs and not just decide on a structure, such as a lower resize threshold meaning fewer collisions but more memory and rehashing being required.

For my investment calculator, I took a single program that I had created and split it into separate components of calculation, reporting, validation, and a test suite that compares new code against the original methods. The calculator returns data instead of printing it, allowing it to become testable and reusable, which it used to not be. In my course planner, I replaced constant CSV loading with a SQLite database. The data is relational, so the prerequisites were designated their own table with an index, keys, constraints, and transactions, leaving the hash table to exist as a fast in-memory copy that gets rebuilt from the new database.

One of my biggest changes throughout personal work and school projects is my attention to defensive coding, going from something I was simply told to do to something that I notice much more often and realize needs fixing. When working on this capstone, this meant validating inputs, finding and fixing undefined behavior, using prepared statements to avoid SQL injection, and using foreign keys and transactions to protect data integrity.

These courses and projects have shaped where I want to go in my career. I have taken a strong interest in backend or full-stack development, and I want my work to be code that is secure, readable, tested, and true to itself, not hiding any of its limitations so it can be improved upon. This portfolio showcases my professional development in the world of programming and allows me to be proud of myself for how I have built a stronger mindset for these seemingly smaller issues.

### How Artifacts Fit Together

In my artifacts, Enhancement One is on its own, being one project for one enhancement, which is my investment calculator that was rebuilt into separate, tested components. Enhancement Two and Three were both built using my course planner program, giving it a better hash table and prerequisite graph to start, then building a SQLite database that keeps the hash table for faster in-memory work.

Each of my pages has links to the coding file sections, allowing you to view the original projects, my first iteration of enhancement, and then a more worked and polished version built off of instructor feedback. Together, these artifacts cover designs, algorithms, databases, security, and the way I used feedback to work with my programs.
